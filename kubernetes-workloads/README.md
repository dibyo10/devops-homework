## Deployment strategies

```bash
bash kubernetes-workloads/run-strategies.sh
```

Before running, a second terminal can capture the transition:

```bash
kubectl -n hw-workloads get pods -w
```

| Strategy | Implementation | What to check |
| --- | --- | --- |
| Rolling update | Two replicas; maxSurge 1, maxUnavailable 0; change the web response to v2 | New ReplicaSet becomes ready while old one scales down; old ReplicaSet remains with zero replicas |
| Blue-green | Separate blue and green Deployments | The Service selector switches from blue to green; EndpointSlices then point to green Pods |
| Canary | Three stable replicas and one preview replica under one family selector | Both response bodies appear across requests; roughly 25% of connections can reach preview, not a guaranteed exact ratio |
| Recreate | Two replicas with strategy Recreate | Updating the template first scales the old ReplicaSet to zero, then starts the new one; expect downtime |

These are real application updates: the response generated by the container changes even though the NGINX image stays the same. Blue-green and canary use separate Deployments and Service selectors; they are not built-in Deployment strategy values. Native Deployment strategies are RollingUpdate and Recreate. [Deployment documentation](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/).

Check blue before the switch, green after the switch, and roll back with:

```bash
kubectl -n hw-workloads patch service bluegreen -p '{"spec":{"selector":{"app":"bluegreen-blue"}}}'
kubectl -n hw-workloads run blue-check --image=busybox:1.36 --restart=Never --command -- wget -qO- http://bluegreen
kubectl -n hw-workloads logs blue-check
kubectl -n hw-workloads patch service bluegreen -p '{"spec":{"selector":{"app":"bluegreen-green"}}}'
kubectl -n hw-workloads rollout undo deployment/rolling
kubectl -n hw-workloads rollout status deployment/rolling
kubectl -n hw-workloads rollout history deployment/rolling
```

`replicaset.yaml` separately demonstrates a ReplicaSet maintaining two replicas. Deleting one of its Pods causes a replacement; editing only its template does not roll existing Pods.

## Twelve Pod lifecycle examples

```bash
kubectl apply -f kubernetes-workloads/namespace.yaml
kubectl apply -f kubernetes-workloads/pod-lifecycle/
kubectl -n hw-workloads get pods -o wide
kubectl -n hw-workloads describe pods
```

For each YAML, use `kubectl apply -f <file>`, `kubectl get -f <file>` and `kubectl describe -f <file>`. The failure examples intentionally do not become Ready.

| File | Expected observation and cause |
| --- | --- |
| 01-running.yaml | Running, 1/1 Ready; long-lived process |
| 02-pending.yaml | Pending; node selector matches no node |
| 03-succeeded.yaml | Completed display, Succeeded phase; exits 0 and Never restarts |
| 04-failed.yaml | Error display, Failed phase; exits 1 and Never restarts |
| 05-crashloopbackoff.yaml | Repeated exit 1, restart count rises, waiting reason CrashLoopBackOff |
| 06-imagepullbackoff.yaml | Missing tag produces ErrImagePull and later ImagePullBackOff |
| 07-readiness.yaml | Running but 0/1 Ready until the file appears after 20 seconds |
| 08-liveness.yaml | Removing the health file makes the probe fail and restarts the container |
| 09-startup.yaml | Startup probe permits 20-second initialization before liveness begins |
| 10-init-container.yaml | Init runs first, writes shared file; main container prints it |
| 11-multi-container.yaml | 2/2 Ready; sidecar reaches the app through shared localhost |
| 12-termination.yaml | SIGTERM handler prints cleanup messages and exits within grace period |

The table explains intended behavior; actual captured results belong in this project's output and screenshots. Official phases are Pending, Running, Succeeded, Failed and Unknown. CrashLoopBackOff and ImagePullBackOff are container waiting reasons, not additional phases.

```bash
kubectl -n hw-workloads logs lifecycle-init -c setup
kubectl -n hw-workloads logs lifecycle-init -c app
kubectl -n hw-workloads logs lifecycle-multi-container -c sidecar
kubectl -n hw-workloads logs lifecycle-crashloop --previous
kubectl -n hw-workloads get pod lifecycle-liveness -o jsonpath='{.status.containerStatuses}'
kubectl -n hw-workloads logs -f lifecycle-termination
# In a second terminal:
kubectl -n hw-workloads delete pod lifecycle-termination
```

Cleanup only this exercise: `kubectl delete namespace hw-workloads`.
